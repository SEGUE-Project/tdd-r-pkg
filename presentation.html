Why test?

  • Shift from ad hoc testing in the console to automated testing
  • Ensure code correctness
  • Reduce the chance of bugs
  • Prevent regression and ensure continuity
  • Anticipate how the code behaves with unexpected input
  • Avoid making the same mistake again
  • Enforce good code structure
  • Make expectations explicit, even before code is written (we will do this)


When not to test?

  • During exploratory analysis, one-off code, when cost of testing outweighs its benefits.

Types of tests

  • Unit tests check that each function / unit of code does what it is supposed to do given example input.
  • Property-based (fuzz) tests generate unexpected inputs with given properties.
  • Mutation tests introduce small changes (“mutations”) in the code and checks if the tests catch them. If tests pass, you have found a bug!


Useful metric for testing

  • Code coverage checks the percentage of lines of code covered by tests.

Unit tests: example

Unit tests check that each function / unit of code does what it is supposed to do given example input.

The function to test, in R/is_adult.R:

is_adult <- function(age) {
  age >= 18
}

The tests, in tests/testthat/test-is_adult.R:

test_that("is_adult() recognises adults and minors", {
  expect_true(is_adult(30))
  expect_false(is_adult(10))
})

test_that("is_adult() treats 18 as an adult", {
  expect_true(is_adult(18))
})

Property-based tests: example

Property-based (fuzz) tests generate unexpected inputs with given properties.

The function to test:

rescale01 <- function(x) {
  (x - min(x)) / (max(x) - min(x))
}

Instead of fixed inputs, test a property on many generated inputs (here with the quickcheck package):

library(quickcheck)

test_that("rescale01() returns values between 0 and 1", {
  for_all(
    x = numeric_(len = 5),
    property = function(x) {
      expect_true(all(rescale01(x) >= 0 & rescale01(x) <= 1))
    }
  )
})

Generated inputs can expose cases we did not think of, e.g. a constant vector (max(x) == min(x)) gives NaN.

Mutation tests: example

Mutation tests introduce small changes (“mutations”) in the code and checks if the tests catch them. If tests pass, you have found a bug!

A mutation tool makes a small change to the code and re-runs the tests:

# Original
is_adult <- function(age) age >= 18

# Mutant: ">=" replaced by ">"
is_adult <- function(age) age > 18
  • With only expect_true(is_adult(30)) and expect_false(is_adult(10)), the tests still pass: the mutant survives, so the tests are too weak.
  • Adding expect_true(is_adult(18)) makes the tests fail on the mutant.

Tools: muttest for R.

Code coverage: example

Measure which lines of the package are run by the tests with the covr package:

library(covr)

cov <- package_coverage()
cov              # overall percentage and per-file summary
tdd-r-pkg Coverage: 85.71%
R/is_adult.R: 100.00%
R/rescale01.R: 66.67%

High coverage shows that code was run, not that it was checked properly. High coverage is no necessarily equivalent to correct behaviour.

Test-Driven Development (TDD)

Test-driven development (TDD) is a way to write source code that involves writing a test case that fails first, then writing just enough code to make the test pass, then refactoring both the test code and the production code, then repeating with another new test case.

Demo: the task

Write is_leap_year(), which takes a year and returns TRUE if it is a leap year.

We will solve it twice:

  1. Code first, checking ad hoc in the console (non-TDD)
  2. Test first, in small steps (TDD)

Demo without TDD: code first

Write the function:

is_leap_year <- function(year) {
  year %% 4 == 0
}

Check it in the console:

is_leap_year(2024)
#> [1] TRUE
is_leap_year(2023)
#> [1] FALSE

“It works!” … but:

is_leap_year(1900)
#> [1] TRUE   # wrong: 1900 was not a leap year
  • The edge case was only found by chance (or by a user, later)
  • The console checks are not saved: nothing to re-run after a change

Note that with existing code you would start implementing automated testing, useful, most commonly recommended, more than TDD.

Demo with TDD: fail

Write the test first, in tests/testthat/test-is_leap_year.R:

test_that("is_leap_year() recognises leap and non-leap years", {
  expect_true(is_leap_year(2024))
  expect_false(is_leap_year(2023))
})

Run it: it fails because the function does not exist yet.

Error: could not find function "is_leap_year"

Demo with TDD: pass

Write just enough code to make the test pass, in R/is_leap_year.R:

is_leap_year <- function(year) {
  year %% 4 == 0
}

The test passes. Now ask: what else should be true? Add the next test:

test_that("is_leap_year() handles century years", {
  expect_false(is_leap_year(1900))
  expect_true(is_leap_year(2000))
})

It fails on 1900. The edge case is found before the code ships.

Demo with TDD: pass again, then refactor

Make the new test pass:

is_leap_year <- function(year) {
  (year %% 4 == 0 & year %% 100 != 0) | year %% 400 == 0
}

All tests pass. Refactor with a safety net, re-running the tests after each change:

is_leap_year <- function(year) {
  divisible_by <- function(n) year %% n == 0
  (divisible_by(4) & !divisible_by(100)) | divisible_by(400)
}

TDD for a segregration function: dissimilarity index

The goal is to create a function dissim(data), where data is a two-column data frame of counts, with one row per spatial unit.

integrated <- data.frame(
  group_a = c(10, 20),
  group_b = c(10, 20)
)

TDD for a segregration function: write first test

Requirement: identical distributions have (D = 0).

test_that("identical distributions give D = 0", {
  integrated <- data.frame(
    group_a = c(10, 20),
    group_b = c(10, 20)
  )

  expect_equal(dissim(integrated), 0)
})
Error:
! Test failed

The test fails because our function is not implemented.

TDD for a segregration function: create function

Create the function with the smallest possible implementation:

dissim <- function(data) { 
  0 
}

The test passes even though this implementation is obviously wrong.

TDD for a segregration function: second test with a known result

New requirement: different group distributions give the correct D.

test_that("a known uneven distribution gives D = 0.5", {
  uneven <- data.frame(
    group_a = c(30, 10),
    group_b = c(10, 30)
  )

  expect_equal(dissim(uneven), 0.5)
})
Error:
! Test failed

The new test fails because dissim() always returns 0.

TDD for a segregration function: modify the function

Implement the formula

dissim <- function(data) {
  a <- data[[1]]
  b <- data[[2]]

  sum(abs(a / sum(a) - b / sum(b))) / 2
}

TDD for a segregration function: re-run the tests

Run the two tests

test_that("identical distributions give D = 0", {
  integrated <- data.frame(
    group_a = c(10, 20),
    group_b = c(10, 20)
  )

  expect_equal(dissim(integrated), 0)
})

test_that("a known uneven distribution gives D = 0.5", {
  uneven <- data.frame(
    group_a = c(30, 10),
    group_b = c(10, 30)
  )

  expect_equal(dissim(uneven), 0.5)
})
Test passed 🥇

The two tests now pass.

TDD for a segregration function: check for invalid input

New requirement: population counts cannot be negative.

test_that("negative counts are rejected", {
  invalid <- data.frame(
    group_a = c(10, -1),
    group_b = c(10,  1)
  )

  expect_error(dissim(invalid), "non-negative")
})
Error:
! Test failed

The test fails

TDD for a segregration function: update function and test

Incorporate input check into the function and test again.

dissim <- function(data) {
  if (any(data < 0)) {
    stop("Counts must be non-negative.", call. = FALSE)
  }

  a <- data[[1]]
  b <- data[[2]]
  sum(abs(a / sum(a) - b / sum(b))) / 2
}

test_that("negative counts are rejected", {
  invalid <- data.frame(
    group_a = c(10, -1),
    group_b = c(10,  1)
  )

  expect_error(dissim(invalid), "non-negative")
})

The test now passes.

Word of caution: wrapping functions that already exist

  • For this exercise, we developed a simplified function to calculate the Index of Dissimilarity, illustrating the principles of TDD.
  • However, this index is already implemented in existing R packages, such as seg.
  • In software development, we should generally reuse existing functions rather than rewrite them.
  • Developing a new function should therefore be justified by specific requirements that existing implementations do not meet.

Demo: non-TDD vs TDD

Without TDD With TDD
Speed at the start Faster Slower: tests come first
Edge cases Found by chance, if at all Prompted by writing tests
Checks are saved No (console) Yes (re-run any time)
Refactoring Risky Safe, backed by tests
Design Shaped by the implementation Shaped by how the code is used
Effort Less upfront More upfront, less debugging later

Why TDD in this workshop?

  • Writing the test first makes our expectations explicit before any code exists
  • It lets us practise the fail-pass-refactor cycle in small steps
  • The tests we write remain in the package and protect it as it grows

TDD in R Packages

  • Writing the tests in tests/testthat/ and the code in R/
  • Keeping code coverage high
  • Data considerations: usage rights, small size, working with synthetic data and mock tests

Writing tests with GenAI
